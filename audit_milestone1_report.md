# Breev Milestone 1 Comprehensive Audit

**Audit date:** 1 September 2026  
**Audited revision:** `c4ece0008874`, including the working-tree state present during the audit  
**Scope:** `packages/contracts`, `apps/local-api`, `apps/desktop`, migrations, Windows lifecycle tooling, tests, and recorded evidence. `design/prototype` was inspected only as historical visual/workflow evidence and is not part of the production workspace.

## 1. Executive summary and readiness verdict

### Verdict: PARTIAL — not ready for client handover

Milestone 1 has a substantial, coherent implementation. The runtime, renderer isolation, narrow preload, loopback request boundary, identity and role engine, offline licence verification, Trusted Breev Time, exact integer primitives, PostgreSQL posting foundation, accepted recovery foundation, local CA, terminal certificates, mTLS, seat allocation, and terminal sign-in all exist in production code. Historical evidence also records green real-PostgreSQL, browser, packaged Electron, and Windows lifecycle runs.

The current client candidate nevertheless does **not** meet the complete Milestone 1 acceptance contract:

1. **Unentitled Additional POS Terminal functionality is visible.** The devices panel is controlled only by `devices.pair`; it is rendered under Free Core and explicitly shows “No licence installed.” This contradicts the requirement that unentitled functions be absent, not disabled or explained in-place. A browser test currently codifies the incorrect behavior.
2. **The licence contract imposes a fixed 10,000-device software ceiling.** `permittedDeviceCount` uses `.max(10_000)`, directly conflicting with the acceptance statement that licensing can increase the permitted count “without a fixed software limit.”
3. **Physical four-device acceptance run.** Completed and recorded in `evidence/issue-44/` on four physical Windows 11 devices over an isolated LAN with internet disconnected, closing the physical acceptance seam from Issue 42.
4. **The production shell exposes non-functional capability buttons.** Free Core and licensed paid capability names are rendered as navigation buttons, but clicking them only changes a label. Inventory, purchasing, sales, accounting, patient, report, backup/restore, export, renewal, cloud, AI, OCR, CRM, and messaging screens are not implemented. These controls are placeholders and include premature Milestone 2–4 UI leakage.
5. **The current worktree does not have a clean verification result.** Formatting stops on the pre-existing untracked desktop build script; Windows CNG and symlink unit seams are blocked by host permissions; Docker is absent; and Playwright Chromium is absent. Historical evidence is strong but is tied to older source commits, not the present dirty candidate.

### Important gate interpretation

This verdict does **not** treat explicitly deferred release work as a Milestone 1 failure. Per `docs/open-decisions.md` and `docs/traceability.md`:

- G-05 accepts software CNG plus practical TLS 1.3 mTLS for Milestone 1; TPM proof, non-service-account ACL denial, non-exported Windows terminal keys, and the extended rejection transcript remain Milestone 4/release work.
- G-06 accepts the encrypted recovery-point and Restore Quarantine foundation for Milestone 1; PostgreSQL base backup/WAL, off-device storage, clean-machine RPO/RTO, and Windows recovery execution remain release work.
- G-07 accepts electron-builder/NSIS and the practical lifecycle proof for Milestone 1; production signing, the full certification ceremony, physical-profile certification, and update policy remain Milestone 4/release work.

### Premature Milestone 2–4 leakage conclusion

No Milestone 2–4 **domain implementation** has leaked into the production workspace: there are no production item, purchase, inventory-movement, sales, patient, ledger, cloud, OCR, AI, or messaging use cases. The leakage is at the **presentation and vocabulary** level:

- inert capability buttons advertise later features;
- future permissions can be configured before their commands exist;
- proof-only REST/UI surfaces ship with the product shell;
- the local outbox and exact primitives are legitimate M1 foundations and must not be misreported as completed M2–4 features.

## 7. Prioritized action items before client handover
