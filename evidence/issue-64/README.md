Independent reconciliation fixtures precede the synthetic scale fixture. Scale inserts 250,001 additional immutable movements on one product into a disposable database, using an existing frozen receipt source. It tests read volume; it is **not** 250,001 complete posting documents or a journal-reconciliation fixture. Reconciliation instead uses fully posted documents and frozen carrying allocations. A separate 50,000-batch synthetic fixture exceeds the real 24 MiB safeguard: ordinary pages remain available and complete export returns HTTP 413 without partial rows or domain changes. Browser activity paging uses 51 complete receipts posted through the API.

The oversized fixture initially timed out even with refreshed planner statistics. EXPLAIN identified a repeated position aggregate inside a nested join. Positions are now materialized once, and batch introduction is computed in that same aggregate rather than through a separate receipt lookup. The combined fixture also exposed underestimated cardinality and repeated sorted-history scans. Reporting therefore favors hash/merge joins with transaction-local enable_nestloop=off; PostgreSQL retains necessary lateral/indexed nested loops. Integration tests launch the compiled API: two intermediate runs inadvertently used the previous build and are invalid evidence for the latest correction. After rebuilding, all 29 tests across reporting/count/authorization passed, including the combined fixture. The maintained test does not widen the server timeout or force an ANALYZE prerequisite.

The design comparison used [Odoo historical inventory valuation](https://www.odoo.com/documentation/19.0/applications/inventory_and_mrp/inventory/inventory_valuation/operations_valuation.html) as precedent for as-of reporting, while preserving Breev's offline authority and separate activity/balance semantics. PostgreSQL's [timestamp precision](https://www.postgresql.org/docs/current/datatype-datetime.html) requires database cutoff comparisons. Neither precedent sets accounting or pharmacist policy.

## Intermittent failures and readiness

**Count browser:** the earlier reason/evidence failure's original trace was unavailable. Inspection found visibility precedes the initial reason-field focus commit. The maintained scenario now synchronizes on toBeFocused before typing and checks both values before applying. Isolated and full-file runs passed. This proves the current scenario's behavior, but does not establish the earlier failure's cause. That cause remains a readiness blocker; production count behavior was not changed based on inference.

**Packaged recovery:** an initial run failed waiting for Ready after API restart. A five-run repetition then reproduced “Main unavailable” versus “Repair required” once, with a window-close event; four passed. A further five-run repetition with CDP-context tracing and health-request diagnostics passed. The cause remains unresolved. The harness now captures renderer events, health responses/failures, process exit state and bounded Electron stderr alongside the trace. No sleeps, relaxed assertions, disabled tests or test retries were introduced as a remedy. A green final gate cannot erase this blocker.

Physical Windows/Narrator evidence and both unresolved intermittent causes keep PR #201 draft. Client visual approval, G-01/G-02 and release approval remain separate.
