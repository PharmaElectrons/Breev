# ADR 0004 Windows packaging comparison

**Comparison date:** 2026-08-24  
**Status:** Harness implemented; real Windows execution pending. The results below do not claim issue #34 completion.  
**Decision status:** Provisional recommendation only. G-07 remains open for #43 and its later release gates.

## Candidates held constant

Both candidates use Electron 43.4.1, the same `electron-vite` application source, the same offline Node/PostgreSQL/Shawl payload, the same nine-fuse policy, the same disposable signing certificate, two build versions, and the same Windows 11 Pro VM baseline.

## Reproducible execution

On Windows, `tooling/windows/Build-WindowsCandidates.ps1 -RunId ... -SnapshotId ... -RequireSigning` builds and retains two increasing versions of both candidates, hashes them, validates Authenticode state across the configured signing scope, proves signature tamper rejection, and records the fuse wire against the retained executable hash. `Invoke-InstalledRuntimeProof.ps1` exercises the NSIS lifecycle. On a restored indivisible baseline, `Invoke-ForgeCandidateLifecycleProof.ps1` installs, repairs, updates, and uninstalls the Forge MSI and records its missing service integration without disguising that gap.

Signing with the disposable certificate proves ordering, coverage, and tamper detection only. It does not prove a production publisher chain, timestamp service, protected release key, or SmartScreen reputation. Those G-07 gates remain open.

## Provisional recommendation

Retain `electron-vite` + electron-builder + full offline NSIS as the production candidate and remove Forge from the production dependency graph. It is the smaller route to Breev's machine-wide service/database lifecycle and already fits the inherited desktop build. Forge itself is maintained, but its applicable per-machine installer path adds an experimental Vite integration, unsupported WiX 3, archived `electron-wix-msi`, a fuse-plugin compatibility gap, and still lacks the lifecycle authoring Breev needs.

This recommendation becomes evidence-backed for issue #34 only after the checked-in harness produces passing signed Windows results on the certification candidate. Until then it remains provisional.
