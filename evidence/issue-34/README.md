# Issue #34 evidence index

**Current status:** Implementation and host preparation are in progress. This sequence is the release path; milestone-1 acceptance follows the practical lifecycle proof in [`docs/open-decisions.md`](../../docs/open-decisions.md) G-07, recorded by the stakeholder decision of 29 August 2026. No certification result is recorded here until every machine-readable check passes on an activated Windows 11 Pro x64 25H2 disposable guest.

## Authority and safety

Use only synthetic data and a disposable VM/snapshot. Never attach a live pharmacy installation, database, backup, configuration directory, or credential. A development-only or unactivated guest may debug the harness but cannot produce completion evidence.

The CachyOS host recommendation and trust boundary are in [`research/windows-11-pro-from-cachyos.md`](research/windows-11-pro-from-cachyos.md). The G-06 wrapper investigation is in [`research/windows-service-wrapper-candidates.md`](research/windows-service-wrapper-candidates.md). Neither closes G-06 or G-07.

## Evidence sequence

Create `artifacts\windows\evidence\<run-id>` inside the Windows checkout first. Pass explicit output, screenshot, and coordination-marker paths beneath that directory to every proof command; do not rely on ProgramData defaults for retained results.

1. Run `tooling/windows/libvirt/prepare-host.sh`, then `tooling/windows/libvirt/finish-windows-setup.sh`. The wizard creates the pinned `pc-q35-11.1` guest, installs the QEMU Guest Agent, and gates activation, Secure Boot, TPM, BitLocker, servicing, storage, display, and accounts. Do not weaken or bypass Windows requirements.
2. Create one run UUID and one snapshot identifier. In a clean checkout inside Windows, use Node 24.19.0 and pnpm 11.23.0. From elevated PowerShell, create the temporary machine-trusted comparison certificate with `New-ComparisonSigningCertificate.ps1`, then run `Build-WindowsCandidates.ps1 -RunId ... -SnapshotId ... -RequireSigning` in the same session.
3. Power the guest off and run `capture-disposable-baseline.sh` with that run ID, source commit, and snapshot ID. This captures disk, UEFI NVRAM, swtpm state, and domain identity as one unit. Start the guest without opening its console.
4. From elevated PowerShell, run `Invoke-InstalledRuntimeProof.ps1 -DisposableEnvironmentAcknowledged -BitLockerRecoveryCustodyAcknowledged` with the two retained NSIS installers, the comparison certificate thumbprint as `-ExpectedSignerThumbprint`, and the same correlation fields.
5. While the NSIS candidate is healthy, run `prove-asar-integrity.mjs` once against the retained 0.0.1 Builder executable and once against the retained 0.0.1 Forge executable. Pass the distinct candidate name, version, run ID, source commit, and snapshot ID each time.
6. Run `Invoke-LanRefusalProof.ps1 -Action Prepare`. Run `run-lan-peer-proof.sh` on the host; it executes the Node socket probe from the isolated Alpine machine at `192.168.134.2` and transfers only its JSON through QEMU Guest Agent. Run the Windows controller with `-Action Collect` against that result.
7. Run `set-windows-internet.sh disconnect` with the run ID, source commit, and snapshot ID so it records that only the isolated issue-34 interface remains in both the live and persistent domain definitions. Sign in as the dedicated standard user and run `standard-user-proof.mjs` with the protected ProgramData root and correlation arguments. At the same time, run `Invoke-ApiRestartWhileDesktopOpen.ps1` in elevated administrator PowerShell against the same fresh marker paths and run ID. The proof actively requires external HTTPS failure, local health, renderer outage/recovery, and standard-user ACL denials.
8. Sign out and close every VM viewer. Run `Invoke-RebootProof.ps1 -Action Prepare`, then run `reboot-and-observe.sh` from the host without opening the guest console. After the SYSTEM startup task records zero interactive logons and healthy auto services on the new boot, run `Invoke-RebootProof.ps1 -Action Collect`. Restore the NAT adapter with `set-windows-internet.sh restore` and the same correlation arguments only after the offline and no-login proofs are complete.
9. Before powering off, run `transfer-windows-evidence.sh export` with the guest checkout path and the same correlation fields. It asks the guest to reject uncorrelated or secret-like evidence, downloads a hash-verified archive through QEMU Guest Agent, and records a host manifest. Power off and run `restore-disposable-baseline.sh --acknowledge-disposable-restore`.
10. Start the restored guest and run `transfer-windows-evidence.sh import`. It validates the archive and restored machine identity, restores the earlier Windows results, and transfers the correlated host baseline, reboot, offline-network, network-restore, and snapshot-restore JSON into the guest. Then run `Invoke-ForgeCandidateLifecycleProof.ps1 -DisposableEnvironmentAcknowledged` with both retained MSIs, the comparison certificate thumbprint, and the same correlation fields. Its clean baseline precondition prevents Builder services from being credited to Forge; installed-file Authenticode enumeration also catches MakerWix-generated files absent from the retained Packager directory.
11. Download `windows-ci.json` from this commit's successful `windows-candidate-evidence` workflow artifact. Copy the retained 0.0.1 Builder application, correlated `packaging-results.json`, and retained `comparison-signing.cer` to a non-pharmacy physical Windows test computer, then run the non-destructive `Invoke-PhysicalProfileProof.ps1 -PackagingResultPath ... -BuilderApplicationRoot ... -ComparisonCertificatePath ... -PhysicalMachineAcknowledged -BitLockerRecoveryCustodyAcknowledged` gate. It validates the public certificate hash, temporarily trusts it in the test operator's CurrentUser root, requires a valid signed application and matching fuses, launches the isolated application with a temporary profile, and removes the trust entry it added. Destructive installer and service tests remain confined to the disposable VM.
12. Run `Confirm-Issue34Evidence.ps1` with every Windows result, the imported host results, the export/import results, the Windows CI result, and the physical-profile result. It rejects mismatched run IDs, commits, snapshots, machines, installer hashes, executable hashes, candidates, versions, and external gates before mapping acceptance criteria.

Capture PowerShell transcripts for the Windows commands and copy only sanitized JSON, screenshots, and transcripts into a `windows/` child directory. Evidence files must contain no passwords, connection URLs, licence keys, certificate private keys, personal account data, or machine secrets.

## Completion rule

The packaging recommendation in [`packaging-comparison.md`](packaging-comparison.md) remains provisional until the two-version signed Windows build, both lifecycle runs, ASAR tamper tests, service/database recovery, offline standard-user run, LAN refusal, no-login reboot, Windows CI, and physical-profile gate all produce passing results and the final evidence aggregator succeeds. That rule is the release path, and no step of the sequence above is removed.

Milestone 1 does not wait for it. On 29 August 2026 the stakeholder confirmed electron-builder with the offline per-machine NSIS installer as the production path on a practical basis, and set milestone-1 acceptance to the practical lifecycle proof recorded in [`docs/open-decisions.md`](../../docs/open-decisions.md) G-07: a clean install reaches Ready; a machine restart returns to Ready; repair recovers without touching pharmacy data or the pharmacy CA; an injected failure rolls back and preserves any existing data directory; uninstall preserves data, and destructive removal happens only through its separate explicit authorization. That proof runs offline with development/test signing and may run on the unactivated `breev-issue-34-win11` guest. Certification completion in this file still requires the activated guest, the physical-profile gate, and `Confirm-Issue34Evidence.ps1`.
