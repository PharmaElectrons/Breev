# Domain and integrity rules

These rules are authoritative. Module names describe ownership, not mandatory packages or processes.

## Shared transaction model

- Internal identities are UUIDv7 and carry no business meaning. Human numbers use separate pharmacy-wide sequences for each document type and year. Gaps are permitted, audited, and never backfilled, and a number is never silently reused after a failed or voided issue. It does not use device prefixes because the local API is the single allocator. Current local type prefixes are `S`, `P`, `SR`, `PR`, `RV`, and `J`. Cloud subscription billing uses a separate series. Final Iraqi legal/accountant presentation remains gated.
- Drafts are durable, mutable, and versioned. Only an explicit protected action can discard them. They have no posted stock or journal effect.
- The system authorizes each posting command, makes it idempotent, and recalculates it from current authoritative state. One local PostgreSQL transaction creates the immutable document and snapshots, movements, settlement/AP/AR/Cash Box effects, balanced journal, audit facts, idempotency result, and required outbox entries. Any failure rolls back the whole command. An idempotency record scopes to the pharmacy and command kind and stores a canonical request hash: reuse with a different payload is rejected, and concurrent identical requests return the one committed result.
- Posting does not hold a database transaction open across user input, printing, OCR, messaging, cloud, or any other network call. Printing, OCR, messaging, cloud work, and other network calls run as durable post-commit jobs. Those jobs cannot replay the business command.
- The system does not update or delete posted documents, movements, payments, journals, audit facts, consent events, or provider evidence. A Return, Reversal, replacement, or non-financial note is a new linked fact. It has its own identity/number, actor, device, time, reason, evidence, permission, approval, stock/money effects, and printable representation.
- Timestamps persist in UTC; the UI displays the pharmacy's configured local time zone. Accounting and expiry logic store business dates separately from timestamps. Actual creation/posting time is immutable and differs from the source/business date. Inventory/accounting effects default to current posting time. Effective-date backdating requires owner/accountant authority, a named permission, Step-Up Authorization, an open period, a reason, an impact preview, deterministic recalculation, and an audit. Closed periods use a current-period correction.
- Historical views use stored snapshots. They never use current product, supplier, patient, price, cost, template, or rule data.

## Exact quantities, money, and accounting

- Inventory quantity is an integer count of the Product's Inventory Unit. Each product defines its main, sub-, and optional tertiary clinical units with explicit positive integer conversions to that Inventory Unit; every allowed package has such a conversion. The tertiary clinical unit is a real quantity unit — never a reminder-days field — and does not affect sale or purchase stock unless later approved. The system accepts no generic fractional unit unless an approved product unit policy defines it.
- All posted IQD amounts are signed integer fils, where `1 IQD = 1,000 fils`. Normal UI may display whole dinars. REST transports these amounts as decimal integer strings. Authoritative TypeScript and PostgreSQL values use exact integer types. Binary floating point is forbidden for money, rates, quantities, discounts, valuation, tax, tender, or report totals.
- WAC and allocation intermediates keep exact higher precision. The system applies deterministic accountant-approved rounding and remainder allocation only when it produces posted fils. Cash rounding is off. An unavoidable physical-cash difference requires a separate, visible, authorized ledger adjustment.
- Every journal uses double entry and is balanced. Finite, versioned, accountant-approved posting templates translate domain facts. They are not a user-authored rules engine. UI and report code cannot create journal lines.
- The system stores gross, discount, net, tax, tender, due/refund, cost source, valuation method, template version, and all calculations needed to explain a posting as immutable facts.
- Trade, invoice, volume, and prompt-payment discounts that reduce the purchase price also reduce inventory acquisition cost and payable/cash. The system allocates them to eligible lines. Later purchase-price rebates adjust remaining inventory and relevant COGS through new entries. A genuine separate expense reimbursement or financing element posts separately.
- WAC is the pharmacy default. The pharmacy may select FIFO during initial setup after accountant review. Last-purchase cost is reference/pricing data only. A later method change requires owner/accountant approval, an effective date, a revaluation preview, a balanced journal, and an audit. FEFO physical picking remains independent of WAC/FIFO valuation.
- An expired/damaged write-off debits `Expired and Damaged Inventory Loss` and credits Inventory at the exact carrying amount. If the daily job detects it, the write-off posts on the expiry date. Otherwise, it posts on the discovery date. It never changes sales revenue, gross profit/margin, or Cash Box. It appears separately in monthly/yearly net profit. Accountant golden examples validate this confirmed treatment but do not reopen it.
- Reports are filterable, sortable, groupable, and exportable read-only views or projections with drill-down to the underlying documents and audit facts. They reconcile source documents, movements, valuation allocations, settlements, and journals. They recheck tenant, permission, entitlement, and data sensitivity. They do not depend on mutation.

## Catalog, purchasing, and inventory

- The system generates the pharmaceutical display from separate Trade Name → Strength → Dosage Form → Manufacturer fields. It generates the general display from Company → Sub-brand/Series → Type/Use → Property/Degree → Target/Audience → Size/Volume fields. Optional parts skip cleanly. The independent Arabic name appears separately and supports fuzzy search. The system never appends it to the English display.
- Naming templates are configurable and versioned. A privileged exceptional override preserves the old and new values, actor, time, and reason. Product identity and uniqueness use internal ID, SKU, barcode, or registration number. They do not use the display name. Posted names never regenerate.
- A product can have no barcode or can have multiple product/package barcodes. Sequential and fuzzy Arabic and English matching can find it. Packaging is product-specific. Product master owns descriptive/commercial data and controlled sell/online/AI-sharing visibility. It does not own current stock or expiry. A flag alone never exposes restricted data. A Supplier owns its profile, default discount, and accounting-ledger relationship. The system archives or merges referenced products and suppliers. It never hard-deletes them.
- Stock changes only through authorized, reasoned, auditable, append-only movements. The system derives on-hand stock. Product quantity setters and direct batch balance edits are prohibited.
- Batch carries product, lot where required, acquisition/receipt evidence, expiry, status, and physical quantity. FEFO selects eligible batches. The legal/pharmacist gate decides which product classes require lot and complete expiry at receipt. That decision cannot change the confirmed five-control purchase row sequence.
- No post may make stock negative. If physical stock exists but Breev is wrong, an authorized manager posts a counted adjustment first with reason/evidence. The pending sale remains intact, and the system revalidates it.
- Expired, recalled, and quarantined stock creates a non-overridable sale block. Near-expiry stock remains sellable with a visible warning and FEFO selection. A daily idempotent local job re-evaluates dated batches; missed runs are observable and recover on restart. A monthly review lists expired and unresolved blocked stock.
- Quarantine changes availability but recognizes no automatic loss. An owner-approved full/partial supplier return, write-off, or destruction creates a dedicated movement. Postponed quantity remains blocked. Recall loss equals only the carrying amount not recovered from the supplier. A zero-price sale is never a disposition method.
- Every disposition freezes the physical batch, quantity, exact carrying amount, total, valuation method, reason, supporting evidence, actor/device/time, and approval. Only an authorized pharmacist/manager may correct an incorrect expiry. The correction requires Step-Up Authorization and reason/evidence, and it preserves the original value.
- A count is a durable session. It records quantity, physical count, unit conversion, variance, reason, approval, and applied movement. It is not a product edit. Reorder starts as a query or saved candidate basket, not an automated procurement suite.
- The inventory review view is read-only. It supports product/batch filters, expiry/near-expiry/low-stock/blocked flags, a reorder-basket action, permission-gated audited export, and per-product drill-down to the complete movement/value history.

## Sales, prices, settlement, and corrections

- A sale draft stores the selected unit, quantity, selling price, price version/source/capture time, line and invoice discounts, optional patient link, tender intent, and server version. A sale may also include an authorized additional non-catalog item line; it has no stock effect and posts under the approved posting templates. Base price, promotion, customer/contract price list, and manual override remain distinct versioned sources. The system revalidates each source's expiry/entitlement. Suspended drafts survive renderer and service restart.
- Posting always revalidates current permission, entitlement, price policy, stock, batch eligibility, restrictions, tax/posting rules, and WAC/FIFO COGS. An invalid proposed batch is replaced under the approved allocation policy or stops the line for review. A below-cost or exceptional-discount sale requires the named Step-Up permission `pricing.below_cost` under versioned accountant/product-owner thresholds. Preserving a draft price never preserves a stale safety, stock, tax, cost, or accounting fact.
- When a price changes, resume/pre-checkout shows the draft price, current price, difference, version, and total impact. Refresh is the default. Keeping an old price requires the named permission `draft.price.override`, a reason, newest-state revalidation, and a complete audit.
- Cash, credit, and partial/mixed settlement create explicit Cash Box, receivable, or payment facts. Cash Boxes are continuous. Reconciliation snapshots are optional and never required to sell.
- A goods Return starts from the original posted document where possible. It selects quantities, refund/debt effect, reason/evidence, and disposition, then posts a new linked transaction. Posting requires `sales.return.post`. If approved, a no-invoice return uses a distinct elevated permission/evidence path. A mistaken invoice uses a full Reversal and optional replacement under `sales.invoice.reverse`. It does not use a Return or an edit. Both named permissions default to the owner or a delegated trusted manager and require Step-Up Authorization. Thresholds and any additional Dual Control remain gated.
- A printer or drawer failure after commit preserves the posted sale. A reprint uses the immutable snapshot and is audited. Retrying an uncertain API response uses the same idempotency key. It returns the existing result instead of posting again.

## Identity, authorization, entitlement, and devices

- Every execution boundary combines a verified pharmacy/tenant, individually authenticated user, device, permission, and entitlement context. The system strongly hashes or otherwise protects passwords/secrets as appropriate. No hard-coded credential ships. The system never accepts tenant or authority from a caller-controlled body. It denies by default. Hiding something in the UI does not enforce access.
- Tenant identity is immutable on tenant-owned cloud records. It constrains API, query, job, sync, object storage, export, audit, and support access. Cloud PostgreSQL uses verified application scoping and `FORCE ROW LEVEL SECURITY`. Its runtime role neither owns tables nor bypasses RLS.
- High-risk permit and denial outcomes are auditable. Step-Up Authorization does not grant missing authority. A sensitive request has a unique ID, actor/device, Trusted Breev Time, current record/version, bounded lifetime, reason/evidence, and final outcome. Approval rechecks the newest authority/state. The system rejects stale requests. The requester must create a new request instead of forcing the old one through. Dual Control requires a different current approver, has no emergency bypass, and two local users can complete it offline. High-risk health/large exports use Dual Control by default. Dual Control defaults never override the Free Core guarantee: in an installation with only one authorized user, the owner completes the pharmacy's own complete export with Step-Up Authorization and full audit. User, role, licence, and terminal changes require owner or trusted-admin permission with Step-Up Authorization. Granting high privilege, changing the last owner, releasing a terminal seat, and manual journals require the separately approved two-user policy. A manual journal requires an authorized preparer and an accountant/owner approver.
- The Main Pharmacy Computer initiates a terminal pairing session under the named permission `devices.pair` after authorized reauthentication. The session is one-use, attempt-limited, and lasts five minutes. Its QR binds the session, expected server/installation identity, CA fingerprint, and proposed terminal public key. The terminal generates a non-exported keypair. Both devices confirm a matching fingerprint phrase. The local pharmacy CA certifies pharmacy/device/type/licence/serial. Discovery uses link-local mDNS/DNS-SD, with the pairing QR and manual endpoint entry as fallbacks; manual entry changes only location and cannot bypass validation. Discovery publishes only the service type, opaque installation ID, address/port, and minimal protocol metadata. Discovery confers no trust. Every request includes a verified device/session and individual user authentication/authorization. Terminal-to-main requests also require mTLS.
- Revocation is immediately local-authoritative and invalidates trust/sessions offline. Because TLS session resumption and keep-alive connections can outlive certificate validation, every request still consults the current local device record, and revocation also terminates that device's sessions and open connections. Replacement creates a new identity/key. The system never copies old credentials. Certificate renewal uses the authenticated channel. It rechecks device/key possession, revocation, seat, plan/grace, Trusted Breev Time, and policy. Planned CA rotation uses a short, explicit dual-trust deadline and confirmed reissuance. Suspected compromise immediately retires the chain and requires owner-confirmed re-pairing. The CA private key is excluded from backup/export/migration. Disaster recovery creates a new trust domain.
- The signed offline licence binds the pharmacy, main device, plan/features, issue/expiry/grace, and format version. Trusted Breev Time detects rollback as far as the approved threat model permits. Tamper or paid expiry fails closed for paid capabilities and fails open for Free Core/data access. Renewal requires no reinstall or data reconstruction.

## Sync and cloud authority

- Local operation never waits for cloud. A local transaction writes its versioned outbox atomically. Delivery is at least once. Cloud inbox/deduplication, idempotency, checkpoints, backoff, visible backlog/dead letters, and replay-safe handlers make delivery resumable.
- One-Way Sync sends only the approved projection/record allowlist. Cloud has read-only access to posted invoices, returns/reversals, stock/batches, payments/Cash Boxes, and accounting. It cannot repair or resolve these by writing them. Corrections begin as new local transactions.
- A future two-way tier uses explicit Cloud Commands only for a versioned field-ownership allowlist. Candidate fields are approved catalog/pricing/supplier/patient-CRM/template/settings master data, never posted facts. Each field still requires explicit promotion. Each command has a unique identity, pharmacy, requester/device, expiry, expected version, old/requested values, reason, validation outcome, and one status. The expected version is a domain revision, never a timestamp. The allowed statuses are `Pending`, `Applied`, `Rejected`, `Conflict`, `Expired`, and `Cancelled`. Applying a command, recording its outcome, and writing its acknowledgement outbox entry happen in one local transaction; a retry with the same command identity returns the recorded result. `Cancelled` is possible only before local application, and `Conflict`, `Rejected`, and `Expired` are terminal — resolution creates a new command against the current revision. Cloud cannot mark a command `Applied` until the local API accepts and acknowledges it.
- A version mismatch preserves Base, Current Local, and Requested Cloud. Resolution under the named permission `sync.conflict.resolve` may keep the local value, apply the request through a newly validated local command, or merge only fields explicitly proven independent. Last-write-wins, timestamp wins, CRDTs, revision-vector frameworks, and generic auto-merge are prohibited for atomic business facts.
- Plan/licence/provider metadata is cloud-authoritative. Local elevation accepts only signed current grants. Stale cloud data cannot undo a local revocation or locally posted facts.

## Patients, privacy, clinical, and providers

- Ordinary core sales remain anonymous. Necessary transaction identity uses the minimum field set for a documented legal/professional/credit purpose. Creating or linking an optional Patient Profile is a separate action. It never blocks an otherwise valid anonymous sale. Once it has legal/pharmacist approval, the optional profile supports contact/notes, typed allergies/chronic facts, linked medication/purchase history, reminders, and purpose-specific consent history. It does not copy mutable profile detail into posted facts.
- Patient/health data is typed and purpose-limited. Generic notes and browser storage are not a health-record model. Consent is specific to its purpose, policy version, language, destination/provider/region, and authorized representative where applicable. Every grant, denial, or withdrawal is append-only. Withdrawal cancels future and queued optional use. Consent never authorizes staff access.
- Access, sensitive export, merge/link/unlink, correction, consent, provider disclosure, deletion/anonymization, legal hold, support, and break-glass actions require permission and are audited. Pseudonymized or otherwise linkable data is never labeled anonymous. Sensitive export requires verified patient identity/authority — shared-phone control, a copied link, or an integration account is never patient identity or consent — and exports provide human-readable and structured formats. Every record class has a versioned retention policy, starting event, controlled end action, and approved basis for any indefinite retention. A protected, minimal Deletion Ledger/tombstone records outcomes through provider delay/failure, sync, outage, and backup restoration. The system replays holds, revocations, and later security state before Restore Quarantine ends. Support access is disabled by default, ticket-bound, owner-authorized, named, strongly authenticated, least-privilege, read-only by default, time-limited, automatically revoked, and fully audited; shared accounts and standing access are prohibited, and Breev Support cannot independently delete pharmacy records. Break-glass uses stronger authorization, short expiry, owner notification, detailed activity logging, and mandatory post-access review. Detailed periods and legal rights remain gated.
- The Free Core Patient/Invoice link view is local-only, read-only, permissioned, and audited. Detaching/anonymizing an eligible optional link cannot edit, delete, post, reverse, settle, or alter patient, debt, stock, Cash Box, tax, or accounting facts. Any outbound connector is separately entitled. It must declare a versioned purpose, recipient/provider, region/transfer, retention, minimum field allowlist, basis/consent, quota/cost, security terms, and owner approval. Patient/phone/health/prescription/medicine-history/clinical fields are blocked by default. A connector cannot directly edit local facts. Its callback is status-only unless promoted as a Cloud Command.
- Regulatory source and Licensed Clinical Knowledge Source are distinct. Clinical evaluation requires current licensed content, pharmacist-reviewed product mapping, explicit patient facts, versioned deterministic rules, and an immutable evaluation snapshot. Missing/stale prerequisites produce **Not Evaluated**. The Iraqi Essential Drugs List is neither a registration database nor an interaction database. An audited kill switch can disable clinical evaluation at any time without affecting core POS or Regulatory Hard Blocks. Regulatory Hard Blocks are non-overridable. Clinical Alerts are advisory and never diagnose, prescribe, dose, or claim safety.
- Contraindicated/major Clinical Alerts stop the cashier at `Pharmacist review required`. They require a pharmacist's recorded decision. Moderate alerts are visible but non-disruptive. Minor alerts are available on demand. An authorized pharmacist may override an advisory alert only with a reason. Validated Arabic/English production wording states that Breev provides decision support. It does not diagnose, prescribe, provide dosage, or replace professional judgment. The wording also states that the absence of an alert does not confirm safety.
- When Breev selects OCR, it adds only a narrow provider adapter and a test fake. Expected or detected patient data blocks external OCR unless redacted or separately approved. OCR preserves the source hash, field locations/confidence, provider/model/version/region, original/corrected values, reviewer, usage, deletion outcome, and final state. A human confirms critical values against the highlighted source. Breev recalculates locally. The pharmacy's encrypted local invoice image linked to a posted purchase is retained Supplier Invoice Evidence under posted-commercial retention, while provider-held data is still deleted promptly. Offline operation, outage, quota, rejection, or expiry never blocks manual purchase entry.
- Each pharmacy owns its WhatsApp Business identity, dedicated number, templates, opt-ins, content, and attributable charges. Breev is a replaceable adapter. At enqueue and again at send, the system rechecks consent/opt-out, destination, purpose/category, template/version, provider/jurisdiction policy, entitlement, and tenant. Callbacks are authenticated, idempotent, ordering-safe, and audited.
- A future payment adapter uses a provider that currently holds a CBI licence for the exact role. It uses a pharmacy-owned merchant/settlement account. Payment Attempt, invoice, settlement, provider refund, and chargeback are distinct immutable records. A timeout has the status `Unknown`. The system never guesses it. Before retrying, it reconciles the same provider reference. Cash remains available.
- A Breev receipt, PDF, QR, or email is not an Official Electronic Tax Invoice without a validated applicable Iraqi/Kurdistan authority, mandate, specification, certification, and legal/accountant approval. Future submissions preserve exact payload/version/status evidence. They never overwrite the local invoice.
