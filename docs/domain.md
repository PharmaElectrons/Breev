# Domain and integrity rules

These rules are authoritative. Module names describe ownership, not mandatory packages or processes.

## Shared transaction model

- Internal identities are UUIDv7 and carry no business meaning. Human numbers use separate pharmacy-wide sequences for each document type and year. Gaps are permitted, audited, and never backfilled, and a number is never silently reused after a failed or voided issue. It does not use device prefixes because the local API is the single allocator. Current local type prefixes are `S`, `P`, `SR`, `PR`, `RV`, and `J`; a Purchase Invoice Adjustment carries the original invoice number plus a sequential `-A` suffix (`P10025-A01`, `-A02`) instead of its own series. Cloud subscription billing uses a separate series. Final Iraqi legal/accountant presentation remains gated.
- Drafts are durable, mutable, and versioned. Only an explicit protected action can discard them. They have no posted stock or journal effect.
- The system authorizes each posting command, makes it idempotent, and recalculates it from current authoritative state. One local PostgreSQL transaction creates the immutable document and snapshots, movements, settlement/AP/AR/Cash Box effects, balanced journal, audit facts, idempotency result, and required outbox entries. Any failure rolls back the whole command. An idempotency record scopes to the pharmacy and command kind and stores a canonical request hash: reuse with a different payload is rejected, and concurrent identical requests return the one committed result.
- Posting does not hold a database transaction open across user input, printing, OCR, messaging, cloud, or any other network call. Printing, OCR, messaging, cloud work, and other network calls run as durable post-commit jobs. Those jobs cannot replay the business command.
- The system does not update or delete posted documents, movements, payments, journals, audit facts, consent events, or provider evidence. A Return, Reversal, replacement, or non-financial note is a new linked fact. It has its own identity/number, actor, device, time, reason, evidence, permission, approval, stock/money effects, and printable representation.
- Timestamps persist in UTC; the UI displays the pharmacy's configured local time zone. Accounting and expiry logic store business dates separately from timestamps. Actual creation/posting time is immutable and always recorded with the responsible user; the editable document/business date never replaces it. An authorized user may set the document/business date while creating a document or voucher; that date determines placement in statements and reports. Once posted, the business date cannot be edited — corrections use a new linked transaction. Whether and how accounting periods close — and therefore how far back a business date may be set — is accountant-gated under G-01; once a period is closed, posting into it is prohibited and uses a current-period correction.
- Historical views use stored snapshots. They never use current product, supplier, patient, price, cost, template, or rule data.

## Exact quantities, money, and accounting

- Inventory quantity is an integer count of the Product's Inventory Unit — the base unit, meaning the smallest approved sales or movement unit (for example, the strip). Each product also defines its larger package unit(s) with explicit positive integer conversion ratios to the base unit (1 pack = 4 strips: purchasing 1 pack records 4 strips in the base unit; showing packs or strips is UI conversion only). Changing the sales or purchase unit recalculates quantity and price by the packaging ratio without fractional base-unit balances. Each interface can have a default unit (for example, larger for purchasing, smaller for selling), changeable during a transaction where permitted. An optional third unit is stored only for number-of-days or dosage follow-up; it is never an inventory-balance, purchasing, or sales unit. Synchronization transfers integer quantities and transaction identities, never raw decimal balances.
- All posted IQD amounts are signed integer fils, where `1 IQD = 1,000 fils`. Normal UI may display whole dinars. REST transports these amounts as decimal integer strings. Authoritative TypeScript and PostgreSQL values use exact integer types. Binary floating point is forbidden for money, rates, quantities, discounts, valuation, tax, tender, or report totals.
- WAC and allocation intermediates keep exact higher precision. The system applies deterministic accountant-approved rounding and remainder allocation only when it produces posted fils. Cash rounding is off as the engineering default, pending G-01. An unavoidable physical-cash difference requires a separate, visible, authorized ledger adjustment.
- Every journal uses double entry and is balanced. Finite, versioned, accountant-approved posting templates translate domain facts. They are not a user-authored rules engine. UI and report code cannot create journal lines.
- The system stores gross, discount, net, tax, tender, due/refund, cost source, valuation method, template version, and all calculations needed to explain a posting as immutable facts.
- Every purchase invoice stores two cost values: the **Primary Supplier Cost** (the full nominal cost before supplier allowance/discount) and the calculated **Cost After Discount**. The Primary Supplier Cost is the sole basis for inventory valuation, average item cost, and cost of goods sold, and for the supplier's primary accounting balance. Cost After Discount is informational — shown on invoices, reviews, and supplier statements — and never replaces that basis or recalculates historical average cost.
- Each supplier profile holds a default allowance/discount percentage and basic terms. Creating an invoice copies the percentage valid on the invoice date into the invoice as a snapshot, with the allowance amount and Cost After Discount; later changes to the supplier's rate never alter earlier invoices. An additional invoice-specific discount/offer is supported and stored alongside. An exceptional allowance granted at settlement is a separate transaction (see the payment-voucher rule) and never changes item cost or historical averages.
- Phase One uses one costing method: perpetual weighted-average cost (WAC) on the Primary Supplier Cost. Last-purchase cost is reference/pricing data only. FEFO physical picking remains independent of valuation. (The earlier selectable-costing-method idea was not carried into the governing scope; reintroducing method selection is a change request.)
- The system never removes expired or damaged stock automatically: it presents eligible items for review, and a manager or authorized user approves removal of some or all of the quantity or postpones it. An approved write-off debits `Expired and Damaged Inventory Loss` and credits Inventory at the exact carrying amount; as an engineering default pending G-01, its business date is the expiry date when the daily job detected the expiry and the discovery date otherwise. It is neither a sale nor a supplier return, never touches any cash account, and never changes sales revenue or the profit margin of sales themselves; the loss reduces net profit for the period through the separate loss account. Each write-off records user, date, quantity, value, and reason in Item Movement Details.
- Users create and classify accounts and cash drawers from the chart of accounts, with types including cash, expense, capital, supplier, patient receivable, and discrepancies. Main accounts cover: assets (main cash, sales cash, per-employee drawers, card/payment-company accounts, patient receivables, medication inventory, enabled fixed assets); liabilities (supplier accounts and other approved liabilities); equity (capital, owner withdrawals, retained earnings); revenue (medication sales and approved services); cost of sales (COGS); and expenses (configurable operating types such as rent, salaries, internet, utilities, taxes/fees, maintenance, cleaning, refrigeration, plus an extensible "Other Expenses" type, and losses from expired medication). Capital and owner withdrawals are recorded separately from operating expenses. Final account names and classifications remain a client decision in [`open-decisions.md`](open-decisions.md).
- A transfer voucher records From Account, To Account, amount, notes, and the voucher (business) date, with voucher search and previous/next navigation. A supplier payment voucher need not link to one invoice — it may settle several invoices or clear the account to zero. It identifies the source cash account and beneficiary supplier and records the amount paid, actual allowance percentage, actual allowance amount, allowance difference, notes, document date, and user; entering either the allowance percentage or amount calculates the other. Suppliers are never paid by card.
- Allowance at settlement is a separate transaction type, never a purchase return, and never changes item cost, historical allowance percentages, or average cost. When the actual settlement allowance differs from the allowance calculated from invoices, the system posts the gap as an **Allowance Difference**. Golden example: five invoices give a Primary Supplier Cost of 5,000 and calculated Cost After Discount of 4,650 (calculated allowance 350); at settlement the supplier accepts 4,500, so the actual allowance is 500 and the Allowance Difference is 150; the supplier balance reaches exactly zero while every original invoice and historical percentage stays unchanged. Simple case: balance 1,000,000, allowance 1% = 10,000, paid 990,000, balance zero.
- Account statements cover debtor patients, suppliers, employee drawers, the safe/treasury, capital, and every other account. Accounts sort alphabetically or by balance; transactions appear chronologically with document references, and double-clicking a transaction opens the original document per permissions. The supplier statement lists each movement separately — purchase invoice, adjustment, return, payment, allowance, allowance difference — with date, document number, values (both cost values shown explicitly), and running balance; the header totals each movement type plus the current balance, and users select a time period. Reconciled movements may carry a mark, and a setting may hide an invoice and its full return from display once their net effect is zero — both remain in the Ledger and audit trail. The debt-aging report buckets supplier debt at 0–30, 31–60, 61–90, and over 90 days, with payment-reminder days configurable per supplier.
- Every traceable transaction — purchase, purchase adjustment, purchase return, supplier payment, supplier allowance, allowance difference, cash/card/deferred sale, debt collection, expense, expiry/damage write-off, inventory adjustment, capital, withdrawal — records a number, date and time, user, reason where needed, reference document, value, and accounting impact.
- Reports are filterable, sortable, groupable, and exportable read-only views or projections with drill-down to the underlying documents and audit facts. They reconcile source documents, movements, valuation allocations, settlements, and journals. They recheck tenant, permission, entitlement, and data sensitivity. They do not depend on mutation. The essential Phase One catalogue covers: sales (totals, cash, card and commissions, deferred, returns, profitability); purchases/suppliers (purchases, adjustments, returns, allowances, allowance differences, payments, balances, debt aging); items/inventory (quantity, value, average cost, COGS, batches and expiry, consumption, alerts, stocktake and expiry movements); patients, subject to permissions and plan (purchase history, debt and collection, follow-ups, reservations, messages); cash and accounts (drawers, employee balances, transfers, shortages/overages, capital, withdrawals, expenses, liabilities, profits); and user activity/audit. All reports support From/To date-and-time filters, a user filter, and column search, sort, and multi-criteria filtering. Sensitive exports are permission-restricted and may require the owner's password. Final report images and columns within these categories remain a client approval in [`open-decisions.md`](open-decisions.md).

## Catalog, purchasing, and inventory

- A clear control switches an item between the two definition modes. The system generates the pharmaceutical display from separate Trade Name → Strength → Dosage Form → Manufacturer fields, with supporting fields such as scientific/generic name, category, and barcode. It generates the general display from Company → Sub-brand/Series → Type/Use → Property/Degree → Target/Audience → Size/Volume fields. Optional parts skip cleanly. The independent Arabic search name appears below the generated English name and participates in the same search rules. The system never appends it to the English display.
- Naming follows the approved field templates, versioned by Breev; the display name is generated from the fields and is never unrelated free text. Product identity and uniqueness use internal ID, SKU, barcode, or registration number. They do not use the display name. Posted names never regenerate.
- A product can have no barcode or can have multiple product/package barcodes, with actions to suggest a barcode for an item without one and to print barcodes. Smart search accepts Arabic names, English names, and barcodes; is instant; and normalizes letter case, spaces, and simple punctuation. A query splits into parts that must appear in the stored name in the same order, though other words may occur between them; within each part, characters match in sequence and matching is not limited to prefixes. Acceptance example: "panadol gs" returns "Panadol Extra GSK", and "extra" returns every item containing "Extra". Semantic spelling correction and AI search are not included. Packaging is product-specific. Product master owns descriptive/commercial data and controlled sell/online/AI-sharing visibility. It does not own current stock or expiry. A flag alone never exposes restricted data. A Supplier owns its profile, default allowance percentage, terms, and accounting-ledger relationship. The system archives or merges referenced products and suppliers. It never hard-deletes them.
- Items carry manual and automatic state colors for conditions such as missing barcode, low stock, expiry, sale below cost, and FEFO/cold storage. Item Movement Details lists the item's full transaction history — purchases, adjustments, purchase returns, sales, sales returns, stocktakes, and write-offs — each showing its reference document, date, time, user, quantity, and value, with permission-gated drill-down to the original document. A daily matching list proposes up to 10 items per day for review; approved matches leave the batch and incomplete items remain. Subject to permissions, users can edit all item-record data (names, barcodes, packaging, prices); the inventory balance stays read-only and changes only through stocktaking or standard transactions.
- Stock changes only through authorized, reasoned, auditable, append-only movements. The system derives on-hand stock. Product quantity setters and direct batch balance edits are prohibited.
- Batch carries product, lot where required, acquisition/receipt evidence, expiry, status, and physical quantity. FEFO selects eligible batches. The legal/pharmacist gate decides which product classes require lot and complete expiry at receipt. That decision cannot break the uninterrupted keyboard row flow of purchase entry.
- A posted purchase invoice is never edited or deleted. "Edit Invoice" creates a **Purchase Invoice Adjustment** draft linked exclusively to the original: the user corrects a complete copy of the invoice, and on save the system compares the copy with the original and extracts only the differences (Delta). Unchanged lines create no movements; only the difference affects inventory, the supplier account, and values — changing a quantity from 4 to 8 adds only +4, never a second full invoice. Supported reasons are quantity error, price error, invoice-number error, supplier error, and other.
- An invoice can have multiple adjustments with sequential identifiers (for example #10025-A01, #10025-A02). Each records its date, time, user, reason, and quantity/value difference, and users navigate between the original and its adjustments in both directions. Starting an adjustment creates a Draft; leaving it unfinished warns the user (continue or delete the draft). Final approval shows a before-and-after summary with the difference and its impact and requires explicit confirmation. An adjustment after later stock movements is allowed only if its Delta leaves a valid balance and batch state; otherwise saving is blocked and an authorized user resolves the conflict through the appropriate stock adjustment, return, or correction.
- A **Purchase Return** is distinct from an adjustment: goods physically leave the pharmacy for the supplier. Full and partial returns reduce inventory and the supplier balance as separate documents linked to the original invoice, showing its number and date, with navigation both ways. Whether duplicate supplier invoice numbers from the same supplier are blocked or only warned remains a client decision in [`open-decisions.md`](open-decisions.md); until then the default is to warn.
- No post may make stock negative. If physical stock exists but Breev is wrong, an authorized manager posts a counted adjustment first with reason/evidence. The pending sale remains intact, and the system revalidates it.
- Expired, recalled, and quarantined stock creates a non-overridable sale block. Near-expiry stock remains sellable with a visible warning and FEFO selection. A daily idempotent local job re-evaluates dated batches; missed runs are observable and recover on restart. A monthly review lists expired and unresolved blocked stock. (The sale block, recall/quarantine states, and monthly review are pharmacy-safety engineering defaults beyond the written scope; G-02 confirms the exact classes and thresholds.)
- Quarantine changes availability but recognizes no automatic loss. An owner-approved full/partial supplier return, write-off, or destruction creates a dedicated movement. Postponed quantity remains blocked. Recall loss equals only the carrying amount not recovered from the supplier. A zero-price sale is never a disposition method.
- Every disposition freezes the physical batch, quantity, exact carrying amount, total, valuation method, reason, supporting evidence, actor/device/time, and approval. Only an authorized pharmacist/manager may correct an incorrect expiry. The correction requires Step-Up Authorization and reason/evidence, and it preserves the original value.
- A count is a durable session. It records quantity, physical count, unit conversion, variance, balances before and after, employee, date/time, reason, approval, and the applied movement. It is not a product edit. Users may enter the counted balance in the base unit or as a combination of large and small units; the system converts to an integer base-unit quantity.
- The reorder basket accepts items from both the inventory and sales interfaces. Adding an item proposes an order quantity of the approved maximum level minus the current balance, which the user can edit. The basket shows balance, consumption, and risk/expiry indicators, with color warning when the projected level could create surplus or waste. A confirmed order moves the item to an Ordered Items list with status and order date, and it can return to the basket. An optional list of unavailable/out-of-stock items may link to the basket manually. The data model must not preclude future supplier-price integrations, but automatic supplier discovery, live comparison, and API ordering are Phase Two.
- The inventory review view is read-only with no delete action and no direct balance edits. Its sortable columns cover current balance, value, average cost, batches, expiry, minimum/maximum levels, reorder point, consumption rate, and risk indicators; settings and permissions control visibility, and no branch column appears in Phase One. Only the owner can export sensitive inventory and supplier data, through protected export functionality. Per-product drill-down reaches the complete movement/value history.

## Sales, prices, settlement, and corrections

- Each item stores a primary retail price, a wholesale or special price, and a pricing method, defaulting to "sell by price". Every purchase invoice shows the retail price, and the item's method determines field locking: in **By Price** mode the percentage field is unavailable and the retail price is editable on the purchase invoice — once saved, the latest approved retail price becomes the item's current price until the record or a later invoice changes it; in **By Percentage** mode the retail price is locked and the percentage is editable — the system calculates the price from the approved cost and stored percentage. The profit percentage is margin on the selling price, not markup on cost: cost 80 with a 20% margin gives 100 before rounding. Settings can round calculated prices to the nearest 250, 500, or 1,000 IQD, or disable rounding. The wholesale/special price lives in the item record and appears in the item panel — it is not re-entered on each purchase invoice; how it is selected during a sale remains a client decision in [`open-decisions.md`](open-decisions.md).
- A sale below average or approved cost always shows a red warning. A pharmacy setting — disabled by default — can additionally require manager approval to continue; when enabled, continuing uses the named permission `pricing.below_cost` and records the approver. The warning must not rely on color alone.
- A sale draft stores the selected unit, quantity, selling price, price version/source/capture time, line and invoice discounts, optional patient link, tender intent, and server version. A sale may also include an authorized additional non-catalog item line; it has no stock effect and posts under the approved posting templates. Base price, promotion, customer/contract price list, and manual override remain distinct versioned sources. The system revalidates each source's expiry/entitlement. Suspended drafts survive renderer and service restart.
- Posting always revalidates current permission, entitlement, price policy, stock, batch eligibility, restrictions, tax/posting rules, and WAC COGS. An invalid proposed batch is replaced under the approved allocation policy or stops the line for review. Preserving a draft price never preserves a stale safety, stock, tax, cost, or accounting fact.
- When a price changes, resume/pre-checkout shows the draft price, current price, difference, version, and total impact. Refresh is the default. Keeping an old price requires the named permission `draft.price.override`, a reason, newest-state revalidation, and a complete audit.
- Approved payment methods are cash, card/credit, and deferred (on-account) sales for a limited set of known patients — there is no general credit facility for all customers. A cash sale posts to the employee's cash drawer. A card sale records the full sale value as revenue and the receivable in the card/payment-company account, never the physical drawer; when a commission applies, the system stores the sale value, commission, and net received separately, and the commission is a payment-service expense, not a patient discount. A deferred sale posts as a patient receivable, with collection recorded as a separate transaction.
- Cash Boxes are continuous and never lock the sales screen — there is no forced shift open/close cycle. A cash drawer can be assigned to an employee account or created in the employee's name, and, subject to permissions, an employee opens their drawer from any licensed device while the main service runs. The employee drawer is reconciled to zero at the start of work; at the end, the system compares the expected balance with actual cash, transfers the matched amount to the safe/treasury account, and leaves any shortage or overage visible in the drawer or transfers it to a separate discrepancies account. Daily transfers form the audit trail for shortages and overages. Receipt, payment, and transfer transactions record the user, date, and time.
- A goods Return starts from the original posted document where possible. It selects quantities, refund/debt effect, reason/evidence, and disposition, then posts a new linked transaction. Posting requires `sales.return.post`. If approved, a no-invoice return uses a distinct elevated permission/evidence path. A mistaken invoice uses a full Reversal and optional replacement under `sales.invoice.reverse`. It does not use a Return or an edit. Both named permissions default to the owner or a delegated trusted manager and require Step-Up Authorization. Thresholds and any additional Dual Control remain gated.
- A printer or drawer failure after commit preserves the posted sale. A reprint uses the immutable snapshot and is audited. Retrying an uncertain API response uses the same idempotency key. It returns the existing result instead of posting again.

## Identity, authorization, entitlement, and devices

- Every execution boundary combines a verified pharmacy/tenant, individually authenticated user, device, permission, and entitlement context. The system strongly hashes or otherwise protects passwords/secrets as appropriate. No hard-coded credential ships. The system never accepts tenant or authority from a caller-controlled body. It denies by default. Hiding something in the UI does not enforce access.
- Tenant identity is immutable on tenant-owned cloud records. It constrains API, query, job, sync, object storage, export, audit, and support access. Cloud PostgreSQL uses verified application scoping and `FORCE ROW LEVEL SECURITY`. Its runtime role neither owns tables nor bypasses RLS.
- High-risk permit and denial outcomes are auditable. Step-Up Authorization does not grant missing authority. A sensitive request has a unique ID, actor/device, Trusted Breev Time, current record/version, bounded lifetime, reason/evidence, and final outcome. Approval rechecks the newest authority/state. The system rejects stale requests. The requester must create a new request instead of forcing the old one through. Dual Control requires a different current approver, has no emergency bypass, and two local users can complete it offline. High-risk health/large exports use Dual Control by default. Dual Control defaults never override the Free Core guarantee: in an installation with only one authorized user, the owner completes the pharmacy's own complete export with Step-Up Authorization and full audit. User, role, licence, and terminal changes require owner or trusted-admin permission with Step-Up Authorization. Each user holds exactly one role and their permissions are exactly that role's grants; no per-user grant, deny list, or override exists, and a grant change applies to every assigned user on their next request. Role administration (listing roles with their grants, creating or renaming a custom role, changing grants) requires the named permission `identity.roles.manage`; assigning a role to a user requires `identity.users.manage`. A built-in role is identified by its stable key, never by its displayed name, so a custom role cannot become the owner role through its name, and the owner role keeps its database-enforced permission floor. Granting high privilege, changing the last owner, releasing a terminal seat, and manual journals require the separately approved two-user policy. A manual journal requires an authorized preparer and an accountant/owner approver.
- The Main Pharmacy Computer initiates a terminal pairing session under the named permission `devices.pair` after authorized reauthentication. The session is one-use, attempt-limited, and lasts five minutes. Its QR binds the session, expected server/installation identity, CA fingerprint, and proposed terminal public key. The terminal generates a non-exported keypair. Both devices confirm a matching fingerprint phrase. The local pharmacy CA certifies pharmacy/device/type/licence/serial. Discovery uses link-local mDNS/DNS-SD, with the pairing QR and manual endpoint entry as fallbacks; manual entry changes only location and cannot bypass validation. Discovery publishes only the service type, opaque installation ID, address/port, and minimal protocol metadata. Discovery confers no trust. Every request includes a verified device/session and individual user authentication/authorization. Terminal-to-main requests also require mTLS.
- Revocation is immediately local-authoritative and invalidates trust/sessions offline. Because TLS session resumption and keep-alive connections can outlive certificate validation, every request still consults the current local device record, and revocation also terminates that device's sessions and open connections. Replacement creates a new identity/key. The system never copies old credentials. Certificate renewal uses the authenticated channel. It rechecks device/key possession, revocation, seat, plan/grace, Trusted Breev Time, and policy. Planned CA rotation uses a short, explicit dual-trust deadline and confirmed reissuance. Suspected compromise immediately retires the chain and requires owner-confirmed re-pairing. The CA private key is excluded from backup/export/migration. Disaster recovery creates a new trust domain.
- The signed offline licence binds the pharmacy, main device, plan/features, issue/expiry/grace, and format version. Trusted Breev Time detects rollback as far as the approved threat model permits. Tamper or paid expiry fails closed for paid capabilities and fails open for Free Core/data access. Renewal requires no reinstall or data reconstruction.

## Sync and cloud authority

- Local operation never waits for cloud. A local transaction writes its versioned outbox atomically. Delivery is at least once. Cloud inbox/deduplication, idempotency, checkpoints, backoff, visible backlog/dead letters, and replay-safe handlers make delivery resumable.
- One-Way Sync sends only the approved projection/record allowlist, uploading queued records without processing duplicates when connectivity returns. Cloud has read-only access to posted invoices, returns/reversals, stock/batches, payments/Cash Boxes, and accounting. It cannot repair or resolve these by writing them. Corrections begin as new local transactions. The remote pages, columns, and reports require client approval before contract milestone four begins; the baseline proposal is a summary dashboard plus selected inventory, sales, accounts, and report screens. Per-item external-visibility controls decide whether an item may appear in external or web views.
- The documented spreadsheet read/export API exposes only the approved columns from sales invoices linked to a named patient, read-only, with practical Google Sheets connection guidance. Nothing writes back to Breev through it.
- A future two-way tier uses explicit Cloud Commands only for a versioned field-ownership allowlist. Candidate fields are approved catalog/pricing/supplier/patient-CRM/template/settings master data, never posted facts. Each field still requires explicit promotion. Each command has a unique identity, pharmacy, requester/device, expiry, expected version, old/requested values, reason, validation outcome, and one status. The expected version is a domain revision, never a timestamp. The allowed statuses are `Pending`, `Applied`, `Rejected`, `Conflict`, `Expired`, and `Cancelled`. Applying a command, recording its outcome, and writing its acknowledgement outbox entry happen in one local transaction; a retry with the same command identity returns the recorded result. `Cancelled` is possible only before local application, and `Conflict`, `Rejected`, and `Expired` are terminal — resolution creates a new command against the current revision. Cloud cannot mark a command `Applied` until the local API accepts and acknowledges it.
- A version mismatch preserves Base, Current Local, and Requested Cloud. Resolution under the named permission `sync.conflict.resolve` may keep the local value, apply the request through a newly validated local command, or merge only fields explicitly proven independent. Last-write-wins, timestamp wins, CRDTs, revision-vector frameworks, and generic auto-merge are prohibited for atomic business facts.
- Plan/licence/provider metadata is cloud-authoritative. Local elevation accepts only signed current grants. Stale cloud data cannot undo a local revocation or locally posted facts.

## Patients, privacy, clinical, and providers

- Ordinary core sales remain anonymous. Necessary transaction identity uses the minimum field set for a documented legal/professional/credit purpose. Creating or linking an optional Patient Profile is a separate action and never blocks an otherwise valid anonymous sale. The Phase One profile supports contact and profile information, chronic conditions, chronic medications, interests, important notes (allergies, smoking, and similar warnings), cumulative weight history with date/time and BMI where height exists, a patient-specific discount applied automatically to that patient's invoices, and purpose-specific consent history. Sales recorded under the patient automatically populate the medication-purchase history with treatment-continuation/interruption indicators. A Do Not Disturb control stops marketing messages and nonessential reminders, leaving only client-approved essential messages. The profile does not copy mutable detail into posted facts. Exact consent, retention, and legal wording remain gated; the gate cannot remove these Phase One capabilities.
- Follow-up lists order patients by due time — treatment dates, birthdays, reservations — and an item leaves the list when its action completes. An unavailable item can be reserved for a patient; when stock returns, the item appears in the follow-up contact list, and the reservation can be cancelled after sending or delivery. Item instructions (uses per day/week/month, before/after/regardless of food, number of days) feed patient follow-up and reminder scheduling; this logic is ignored when a sale has no named patient.
- Patient/health data is typed and purpose-limited. Generic notes and browser storage are not a health-record model. Consent is specific to its purpose, policy version, language, destination/provider/region, and authorized representative where applicable. Every grant, denial, or withdrawal is append-only. Withdrawal cancels future and queued optional use. Consent never authorizes staff access.
- Access, sensitive export, merge/link/unlink, correction, consent, provider disclosure, deletion/anonymization, legal hold, support, and break-glass actions require permission and are audited. Pseudonymized or otherwise linkable data is never labeled anonymous. Sensitive export requires verified patient identity/authority — shared-phone control, a copied link, or an integration account is never patient identity or consent — and exports provide human-readable and structured formats. Every record class has a versioned retention policy, starting event, controlled end action, and approved basis for any indefinite retention. A protected, minimal Deletion Ledger/tombstone records outcomes through provider delay/failure, sync, outage, and backup restoration. The system replays holds, revocations, and later security state before Restore Quarantine ends. Support access is disabled by default, ticket-bound, owner-authorized, named, strongly authenticated, least-privilege, read-only by default, time-limited, automatically revoked, and fully audited; shared accounts and standing access are prohibited, and Breev Support cannot independently delete pharmacy records. Break-glass uses stronger authorization, short expiry, owner notification, detailed activity logging, and mandatory post-access review. Detailed periods and legal rights remain gated.
- The Free Core Patient/Invoice link view is local-only, read-only, permissioned, and audited. Detaching/anonymizing an eligible optional link cannot edit, delete, post, reverse, settle, or alter patient, debt, stock, Cash Box, tax, or accounting facts. Any outbound connector is separately entitled. It must declare a versioned purpose, recipient/provider, region/transfer, retention, minimum field allowlist, basis/consent, quota/cost, security terms, and owner approval. Patient/phone/health/prescription/medicine-history/clinical fields are blocked by default. A connector cannot directly edit local facts. Its callback is status-only unless promoted as a Cloud Command.
- Regulatory source and Licensed Clinical Knowledge Source are distinct. Clinical evaluation requires current licensed content, pharmacist-reviewed product mapping, explicit patient facts, versioned deterministic rules, and an immutable evaluation snapshot. Missing/stale prerequisites produce **Not Evaluated**. The Iraqi Essential Drugs List is neither a registration database nor an interaction database. An audited kill switch can disable clinical evaluation at any time without affecting core POS or Regulatory Hard Blocks. Regulatory Hard Blocks are non-overridable. Clinical Alerts are advisory and never diagnose, prescribe, dose, or claim safety.
- Contraindicated/major Clinical Alerts stop the cashier at `Pharmacist review required`. They require a pharmacist's recorded decision. Moderate alerts are visible but non-disruptive. Minor alerts are available on demand. An authorized pharmacist may override an advisory alert only with a reason. Validated Arabic/English production wording states that Breev provides decision support. It does not diagnose, prescribe, provide dosage, or replace professional judgment. The wording also states that the absence of an alert does not confirm safety.
- When Breev selects OCR, it adds only a narrow provider adapter and a test fake. Expected or detected patient data blocks external OCR unless redacted or separately approved. OCR preserves the source hash, field locations/confidence, provider/model/version/region, original/corrected values, reviewer, usage, deletion outcome, and final state. A human confirms critical values against the highlighted source. Breev recalculates locally. The pharmacy's encrypted local invoice image linked to a posted purchase is retained Supplier Invoice Evidence under posted-commercial retention, while provider-held data is still deleted promptly. Offline operation, outage, quota, rejection, or expiry never blocks manual purchase entry.
- Breev Company selects, contracts for, controls, and administers production hosting, AI/OCR provider accounts, and the WhatsApp platform relationship, and may resell those services to pharmacies at its own prices and margins; all external-service charges are excluded from the development price. Each pharmacy receives a segregated WhatsApp business identity, number, templates, consent records, usage attribution, and audit trail administered by Breev — no cross-pharmacy pooling of identities, numbers, templates, or opt-ins. Legal titling of each WABA/number and the billing arrangement follow Meta's or the approved partner's requirements at activation; a provider-mandated customer-held asset does not change Breev's provider contract and resale role. Messaging sends immediately or on schedule from approved templates, and users with permission can add a new template from the interface. At enqueue and again at send, the system rechecks consent/opt-out, destination, purpose/category, template/version, provider/jurisdiction policy, entitlement, and tenant. Callbacks are authenticated, idempotent, ordering-safe, and audited. There is no unified conversation inbox, chatbot, or unrestricted Meta access.
- A future payment adapter uses a provider that currently holds a CBI licence for the exact role. It uses a pharmacy-owned merchant/settlement account. Payment Attempt, invoice, settlement, provider refund, and chargeback are distinct immutable records. A timeout has the status `Unknown`. The system never guesses it. Before retrying, it reconciles the same provider reference. Cash remains available.
- A Breev receipt, PDF, QR, or email is not an Official Electronic Tax Invoice without a validated applicable Iraqi/Kurdistan authority, mandate, specification, certification, and legal/accountant approval. Future submissions preserve exact payload/version/status evidence. They never overwrite the local invoice.
